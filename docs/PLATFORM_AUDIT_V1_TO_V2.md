# KIRO Platform — аудит v1 и план перехода к v2

**Дата:** 27.10.2026 · **Репозиторий:** `platform` (ветка `main`, 344 коммита) · **Продакшен:** kiroplatform.ru

Документ для команды разработки. Цель — зафиксировать, что у нас есть сейчас, где слабые места, и какие задачи ставить для второй версии платформы: большая аудитория, высокая нагрузка, горизонтальное масштабирование, безопасность, аналитика.

> **Как читать.** Раздел 2–5 — факты, проверенные по коду репозитория. Данные о сервере (1 ядро / 1 ГБ / 10 ГБ) и бэкапах взяты из существующего `docs/kiro-system-design.html` и по коду не проверялись. Целевые цифры нагрузки в разделе 8 — **допущения**, их нужно подтвердить с продуктом. Что не проверялось — помечено «не проверено».

## 1. Краткое резюме

KIRO — монолит на одном VPS: React SPA + один процесс Node.js/Express + один файл SQLite. Платформа выросла из лагеря на 3 месяца в многопрофильную: лагеря (лето/осень), программы по направлениям (backend, ML, системный анализ, безопасность, продукт, бизнес), курсы (Python, алгоритмы, математика), тренажёры, соцсеть (стена, подписки, личные сообщения), анкеты знакомств, вакансии, запись на созвоны, проверка ДЗ, аналитика, админка.

**Для текущей аудитории (сотни пользователей) это работает и местами сделано аккуратно** (песочница SQL-тренажёра, транзакционная запись на слоты, санитизация аналитики, внешний watchdog). **Для роста на порядки архитектура не подходит**, причём главные ограничения — не CPU, а:

1. один сервер и один процесс — единая точка отказа, нет отката и staging;
2. SQLite с синхронным драйвером — один писатель, блокирует event loop, не масштабируется на несколько инстансов;
3. модель данных «зашита» под конкретные лагеря (`is_summer_camp_2026`, `is_autumn_camp_2026`);
4. весь учебный контент (~9 МБ исходников, 284 файла) лежит во фронтенд-репозитории и собирается в бандл;
5. слабый периметр безопасности (нет лимитов на логин, JWT в localStorage, секреты админов в открытом виде, БД в git);
6. нет тестов, линтера, типов, CI-проверок, наблюдаемости кроме health-check.

**Главная рекомендация.** Не бросаться сразу в микросервисы. Сначала — «фундамент» (PostgreSQL, Redis, контейнеры, CI/CD со staging, безопасность), затем — **модульный монолит** с чёткими границами доменов, и только потом выделять сервисы там, где у домена разная нагрузка или жизненный цикл (аналитика, исполнение кода, realtime/уведомления, медиа). Подробности — разделы 7–9.

## 2. Что есть сейчас

### 2.1 Стек

| Слой | Технологии |
|---|---|
| Фронтенд | React 18.3, Vite 5, react-router-dom 7, KaTeX. Только JavaScript (без TypeScript) |
| Бэкенд | Node.js + Express 4, better-sqlite3 (синхронный), jsonwebtoken, bcryptjs, multer, AWS SDK (S3) |
| База | SQLite (WAL), файл `backend/data/kiro.db`; отдельная `sql-trainer.db` (4 МБ) для SQL-тренажёра |
| Файлы | S3-совместимое хранилище reg.ru (аватарки, картинки постов); учебные файлы (ноутбуки, CSV, 5 МБ) лежат в `backend/files/` |
| Исполнение кода | Python — Pyodide в Web Worker в браузере (скрипты с jsDelivr); SQL — отдельный дочерний процесс на сервере |
| Админка | Vanilla JS (~3,7 тыс. строк) в `backend/admin/`, отдаётся тем же процессом на `/admin` |
| Деплой | GitHub Actions → сборка фронта → `scp` на VPS; на сервере `pm2 reload kiro-backend` |
| Мониторинг | `monitor-bot` (Telegram, на самом сервере) + GitHub Actions `watchdog` раз в 5 минут снаружи |

### 2.2 Масштаб кодовой базы

- Фронтенд: 101 файл логики (`pages` — 35 страниц, `components` — ~40), 284 файла контента (`src/data`, `src/theory`, `src/questions`).
- Бэкенд: 22 файла маршрутов, ~111 эндпоинтов, ~5,5 тыс. строк. `db.js` — 1159 строк (схема, миграции, начальные данные в одном файле).
- БД: 28 таблиц.
- Бандл: главный чанк `index-*.js` — 1,4 МБ (до gzip), всего 187 файлов в `dist`; 110 мест с ленивой загрузкой.
- Тестов нет, линтера нет, типизации нет, Dockerfile нет, OpenAPI нет.

## 3. Что сделано хорошо (сохранить в v2)

- **SQL-тренажёр изолирован**: отдельный процесс, `readonly` + `query_only`, запрет `RECURSIVE`, ограничения на `randomblob/zeroblob/replace/group_concat`, таймаут и сторож памяти. Готовый прообраз сервиса исполнения кода.
- **Запись на созвоны** — через транзакцию с условным `UPDATE … WHERE booked_by IS NULL`: гонка слотов обработана корректно.
- **Аналитика** принимает только белый список событий и полей, не хранит текст решений/сообщений, не ломает UX при сбое (всегда `204`), на фронте — очередь с пачками, idle-детектор, вкладка в фоне не считается.
- **Файлы программ**: проверка пути (`startsWith(FILES_DIR)`), проверка принадлежности к направлению.
- **Роли админки** с областями доступа (`full / homework / tasks / producer`), админ-токен живёт 24 ч, пароли админов — в `.env`, а не в коде.
- **Наблюдаемость минимума**: `/api/health` с проверкой БД, закрытый `/api/health/details` (сравнение ключа через `timingSafeEqual`), внешний watchdog, не зависящий от нашего сервера.
- **Миграции аддитивные и идемпотентные** (`CREATE … IF NOT EXISTS`, `ADD COLUMN` по проверке `PRAGMA table_info`).
- **Тяжёлые вещи вынесены**: Python — в браузер, картинки — в S3, видео — на YouTube.

## 4. Проблемы и риски

Приоритеты: **P0** — исправить сразу, независимо от v2; **P1** — блокирует рост; **P2** — технический долг.

### 4.1 Безопасность

| # | Приор. | Проблема | Подробности |
|---|---|---|---|
| S1 | **P0** | База и служебные файлы в git | `backend/data/kiro.db`, `-wal`, `-shm` отслеживаются git, хотя `backend/data/` есть в `.gitignore`. В истории — хеши паролей и данные пользователей. Также в git: **2233 файла `node_modules/`**, 188 файлов `dist/`, `.DS_Store`. Нужно: удалить из индекса, вычистить из истории (`git filter-repo`), **считать скомпрометированными** всё, что там было (сменить `JWT_SECRET`, пароли админов), проверить, что в историю не попадали `.env` |
| S2 | **P0** | Нет защиты от перебора пароля | У `/api/auth/login` и `/api/auth/admin-login` нет лимитов и блокировок. Лимит есть только на регистрацию |
| S3 | **P0** | Лимит регистрации, вероятно, сломан за прокси | `registerRateLimit` ключуется по `req.ip`, а `app.set('trust proxy', …)` нигде не задан. За nginx все запросы могут приходить с `127.0.0.1` — тогда лимит «5 регистраций за 15 минут» **общий на всех**. Проверить по конфигу nginx (не проверено) |
| S4 | P1 | Админские пароли в открытом виде | `adminAccounts()` читает пароли из env и сравнивает через `===` (не constant-time). Нет хеширования, 2FA, журнала действий, блокировки, смены пароля. `TASK_ADMINS` не допускает запятых в пароле |
| S5 | P1 | JWT в `localStorage` | Любая XSS → кража сессии на 14 дней. Нет refresh-токенов, нет отзыва токена (logout/смена пароля/бан не инвалидируют). Есть 7 мест с `dangerouslySetInnerHTML` (`LessonBlocks`, `ProgramBlocks`, `day-25-security`, `backend-5`, `security-3`) и нет CSP |
| S6 | P1 | Нет HTTP-заголовков безопасности | Нет `helmet`, CSP, `X-Frame-Options`, HSTS (возможно, часть задана в nginx — не проверено) |
| S7 | P1 | CORS | `origin: process.env.FRONTEND_URL \|\| '*'` вместе с `credentials: true` — при пустой переменной получаем небезопасный fallback на `*` |
| S8 | P1 | Утечка внутренних ошибок | 28 мест с `res.status(500).json({ message: e.message })` — наружу уходят тексты ошибок БД/ФС |
| S9 | P1 | Нет валидации входных данных единым слоем | Проверки ручные, в каждом роуте по-своему; нет схем (zod/joi/ajv) |
| S10 | P1 | Нет восстановления доступа | В `auth.js` только `login / register / admin-login`: нет сброса пароля, подтверждения email, смены пароля. Email при регистрации — заглушка `<ник>@kiro.local` |
| S11 | P1 | Закрытые материалы доступны по прямым URL | Весь контент — статические чанки фронтенда. Скрытие «до даты» и «только для направления» реализовано на клиенте (в `PROJECT_CONTEXT.md` — `new Date(...) <= today`). Любой, кто знает URL чанка, прочитает материал до даты. Не проверено для каждой страницы, но архитектурно неизбежно |
| S12 | P1 | Персональные данные и правовые риски | Платформа хранит ники, ДР, фото, личные сообщения, анкеты знакомств. Для РФ — 152-ФЗ (локализация, согласия, политика, право на удаление). Если есть несовершеннолетние участники — отдельные требования. Фото в S3 с `ACL: public-read`, сообщения хранятся открытым текстом. Раздел «Знакомства» требует отдельного решения команды (модерация, возрастные ограничения, жалобы). Нужна консультация юриста |
| S13 | P2 | Вход по `email OR name OR nickname` | Поле `name` не уникально; запрос берёт первую найденную строку. Рекомендуется один идентификатор входа |
| S14 | P2 | Зависимости | Не проверялись `npm audit`/Dependabot; в CI используется `npm install`, а не `npm ci` — сборки невоспроизводимы |
| S15 | P2 | Загрузка файлов | Тип проверяется по `mimetype`/расширению, содержимое — нет (магические байты); нет антивируса/ресайза; `multer.memoryStorage` с лимитом 5 МБ × число одновременных загрузок = риск по памяти на 1 ГБ |

### 4.2 Масштабирование и производительность

| # | Приор. | Проблема | Подробности |
|---|---|---|---|
| P1 | P1 | Единая точка отказа | Один сервер, один процесс, нет резервного. Недавний инцидент — зависание из-за нехватки памяти (по `kiro-system-design.html`) |
| P2 | P1 | SQLite | Один писатель, файл на одной машине → нельзя запускать несколько инстансов API. `better-sqlite3` синхронный: тяжёлый запрос блокирует event loop всего процесса. Нет пулов, реплик, PITR |
| P3 | P1 | Состояние в памяти процесса | Лимиты (регистрация, аналитика, SQL-тренажёр) лежат в `Map` внутри процесса → при втором инстансе и при рестарте они ломаются/сбрасываются |
| P4 | P1 | Опрос (polling) вместо push | Бейджи — каждые 30 с, чат — 10–15 с, проверка токена — 60 с, аналитика — 30 с. По оценке `kiro-system-design.html`: 40–50 запросов/с на 300 онлайн; на 5–10 тыс. онлайн это 700–1500 запросов/с «ради пустоты» |
| P5 | P1 | Аналитика в той же БД, что и боевые данные | `analytics_events` растёт неограниченно (нет TTL/партиционирования/агрегатов), сводки считаются запросами по сырым событиям + рабочим таблицам, прямо в процессе API |
| P6 | P1 | Запрос списка диалогов | `GET /api/messages` использует коррелированный подзапрос с `GROUP BY CASE …` по всей переписке пользователя; при росте сообщений нужен денормализованный `conversations` и курсорная пагинация |
| P7 | P1 | Контент вшит во фронтенд | ~9 МБ исходников, `homeworkContent` 192 КБ, главный чанк 1,4 МБ. Любая правка текста = коммит + сборка + деплой. Нет версионирования/черновиков/превью. Условия ДЗ дублируются в `backend/src/data/homework-conditions.json` (генерируется скриптом `gen-homework-conditions.mjs`) |
| P8 | P2 | Нет кэширования | Нет Redis/кэша ответов, нет CDN перед статикой/API (по документу — «в планах»). Публичные GET (`schedule`, `library`, `announcements`, `links`) отдаются из БД каждый раз |
| P9 | P2 | Нет сжатия/ETag/пагинации системно | `compression` не подключён (возможно, сжимает nginx — не проверено); пагинация в разных роутах разная |
| P10 | P2 | Файлы программ на диске сервера | `backend/files/` — 5 МБ в git и на диске API; при нескольких инстансах разъедутся |
| P11 | P2 | Pyodide с внешнего CDN | При недоступности jsDelivr (в т.ч. блокировки в РФ) ломаются тренажёры Python |

### 4.3 Архитектура и модель данных

| # | Приор. | Проблема |
|---|---|---|
| A1 | **P1** | **Год и набор «зашиты» в схему**: колонки `users.is_summer_camp_2026`, `users.is_autumn_camp_2026`, `autumn_direction`; `startDate: '2026-06-01'` и `totalTasks: 15` захардкожены в `auth.js`. Каждый новый набор потребует новых колонок и правок кода. Нужна модель `programs / cohorts / enrollments` |

| A3 | P1 | Роли и права: `role` + `scope` в токене — грубая модель (4 фиксированные области). Нужны RBAC с правами, привязка админа к БД (сейчас админ вообще не строка в `users`, поэтому в `notify()` для системных уведомлений приходится обходить `actor_id`) |

| A5 | P2 | Миграции и сидирование внутри `db.js` (1159 строк), выполняются при импорте модуля. Нет версионирования миграций, нет отката |

| A8 | P2 | Админка — отдельное vanilla-JS приложение без сборки и общего кода с основным фронтендом |

## 5. Анализ текущей аналитики

**Что собирается.** События с фронта (`session_start`, `page_view`, `material_open`, `quiz_answer`, `code_run`, `split_open`, `video_play`, `level_test_finish`, `math_solution_open`), активное время по разделам (`analytics_time`), плюс бизнес-факты из рабочих таблиц (регистрации, сдачи и проверки ДЗ, посты, сообщения, записи на созвоны). Отображается на дашборде админки за 7/30/90 дней; даты считаются по Москве.

**Чего не хватает для v2:**

- Нет хранилища для аналитики — всё в OLTP-базе, нет агрегатов и очистки.
- Нет единой схемы событий (имена, версии, обязательные поля), нет трекинга источников трафика (UTM), воронок «лендинг → регистрация → первое действие».
- Нет когортного анализа и retention (D1/D7/D30), нет метрик обучения: время до первой сдачи ДЗ, доля завершения глав, SLA проверки ДЗ, «зоны отвала» по урокам.
- Нет продуктовых экспериментов (A/B, feature flags).
- Нет технических метрик в одном месте (латентность API, ошибки, очереди).
- Нет экспорта в BI (Metabase/Superset/DataLens) и самообслуживания для продукта.
- Нет учёта согласий пользователей на сбор данных.

## 6. Принципы v2

1. **Сначала надёжность, потом гранулярность.** Микросервис без своей БД, CI и мониторинга — это распределённый монолит с худшей отладкой.
2. **Модульный монолит как промежуточная цель.** Границы доменов фиксируем в коде и контрактах; выделяем в отдельный сервис только то, что этого требует (нагрузка, изоляция, другой стек, разная частота релизов).
3. **Stateless-приложения.** Любое состояние — в PostgreSQL, Redis, объектном хранилище. Любой инстанс можно убить.
4. **Контент отделён от кода.** Учебные материалы — данные с версиями, а не файлы в бандле.
5. **Безопасность по умолчанию.** Централизованная аутентификация/авторизация, секреты в хранилище, аудит.
6. **Наблюдаемость с первого дня:** метрики, логи, трейсы, алерты, SLO.
7. **Всё воспроизводимо:** контейнеры, IaC, миграции, `npm ci`.

## 7. Целевая архитектура v2

### 7.1 Общая схема

```
Клиенты: Web SPA (TS) · Admin SPA · (позже) мобильное приложение
        │
   CDN + WAF (статика, кэш публичных GET, защита от ботов/DDoS)
        │
   API Gateway / Ingress (TLS, rate limit, auth-проверка JWT, роутинг, request-id)
        │
 ┌──────┴────────────────────────────────────────────────────────────┐
 │ Сервисы / модули домена                                           │
 │  Identity & Access │ Users & Profiles │ Content (LMS)             │
 │  Learning (прогресс, ДЗ, проверка) │ Scheduling (созвоны, слоты) │
 │  Social (стена, подписки, чат) │ Notifications │ Media          │
 │  Code Execution (SQL/Python sandbox) │ Analytics │ Admin BFF     │
 └──────┬──────────────┬──────────────┬─────────────┬───────────────┘
        │              │              │             │
   PostgreSQL     Redis (кэш,    Брокер событий   S3 + CDN
 (primary+реплика, лимиты,      (NATS/RabbitMQ/   (медиа, файлы
  PgBouncer,       сессии,       Kafka-lite)       программ)
  PITR-бэкап)      pub/sub)          │
                                     ▼
                         ClickHouse (аналитика) → BI (Metabase)
Наблюдаемость: Prometheus + Grafana · Loki/ELK · OpenTelemetry · Sentry · Alertmanager → Telegram
```

### 7.2 Границы доменов и что с ними делать

| Домен / сервис | Ответственность | Хранилище | Выделять отдельно? |
|---|---|---|---|
| **Identity & Access** | Регистрация, вход, токены, refresh, сброс пароля, 2FA для админов, RBAC, аудит входов | PostgreSQL (своя схема) + Redis (отзыв токенов, лимиты) | Да — раньше всех: от него зависят все остальные, у него особые требования к безопасности |
| **Users & Profiles** | Профиль, аватар, настройки, согласия, приватность | PostgreSQL | Модуль (позже сервис) |
| **Content (LMS)** | Программы, потоки (cohorts), недели, уроки, квизы, версии, публикация, доступ по дате/когорте | PostgreSQL + S3 (вложения) | Модуль; контент через API/CMS, а не в бандле |
| **Learning** | Прогресс, ДЗ, проверка, комментарии проверяющих, очки/серии/лидерборд, трофеи | PostgreSQL | Модуль → сервис при росте очереди проверки |
| **Scheduling** | Созвоны, слоты, бронирование, напоминания | PostgreSQL | Модуль |
| **Social** | Посты, комментарии, реакции, подписки, личные сообщения | PostgreSQL (+ Redis для ленты) | Сервис (разный профиль нагрузки) |
| **Realtime / Notifications** | WebSocket/SSE, push, email, Telegram; бейджи и чат без polling | Redis pub/sub, очередь | **Да** — убирает polling, главный источник лишних запросов |
| **Media** | Presigned-загрузки в S3, ресайз, проверка типа, модерация | S3 + очередь обработки | Сервис-воркер |
| **Code Execution** | SQL (серверный sandbox), Python (WASM в браузере; при необходимости серверный sandbox: gVisor/Firecracker) | Отдельная read-only БД, без сети | **Да** — другая модель рисков и ресурсов |
| **Analytics** | Приём событий → очередь → ClickHouse; агрегаты, воронки, retention, выгрузки | ClickHouse + PostgreSQL (метаданные) | **Да** — не должна влиять на OLTP |
| **Admin BFF** | Агрегация данных для админки, права, аудит действий | — | Модуль |

### 7.3 Данные

- **PostgreSQL** вместо SQLite: транзакции, JSONB, партиционирование, репликация, PITR. Миграции — через инструмент (Prisma Migrate / node-pg-migrate / Flyway) с версиями. Подключение через PgBouncer.
- **Новая модель доступа к программам** (устраняет A1/A2): `programs` → `cohorts` (набор: даты, лимиты) → `enrollments` (user, cohort, роль, статус, дата) → `entitlements` (что открыто). Вместо `is_*_camp_2026`.
- **Единая модель ДЗ**: `assignments` (из Content) → `submissions` → `reviews`; один процесс для всех программ (устраняет A7).
- **Единая модель прогресса**: события `progress` (user, item, status, score, ts) + агрегаты; `localStorage` — только кэш.
- **Сообщения**: таблица `conversations` + курсорная пагинация, индексы по `(conversation_id, id)`.
- **Уведомления**: outbox-паттерн (запись в той же транзакции → воркер доставляет).
- **Аналитика**: `analytics_events` уезжает в ClickHouse с TTL; сырые события 13 месяцев, агрегаты — бессрочно.
- **Бэкапы**: ежедневный base-backup + WAL-архив, хранение в отдельном S3/регионе, **регулярная проверка восстановления** (раз в месяц).

### 7.4 Безопасность v2

- **Аутентификация:** access-токен (5–15 мин) + refresh-токен в `httpOnly; Secure; SameSite` cookie с ротацией и списком отзыва; Argon2id для паролей; lockout/экспоненциальная задержка и CAPTCHA на логин; сброс пароля и подтверждение email; опционально вход через OAuth (Google/Telegram/GitHub).
- **Админы:** учётные записи в БД (не в env), Argon2id, обязательная 2FA (TOTP), SSO при наличии; отдельный домен/сеть для админки (VPN или IP allow-list); **журнал аудита** всех изменяющих действий.
- **Авторизация:** RBAC/ABAC с явными правами (`homework.review`, `content.edit`, `users.ban`, …), проверка на уровне сервиса, а не только в роутере.
- **Периметр:** WAF, rate limit на шлюзе (по IP + пользователю, в Redis), CSP со строгими политиками, HSTS, `helmet`, запрет `*` в CORS, санитизация HTML (DOMPurify) во всех местах `dangerouslySetInnerHTML`.
- **Данные:** шифрование на диске и в бэкапах, TLS внутри сети, минимизация PII, срок хранения, «право на удаление», согласия, отдельное хранение ключей (Vault/KMS/Yandex Lockbox). Приватные бакеты S3 + presigned URL вместо `public-read` для всего, что не должно быть публичным.
- **Контент:** материалы по датам/доступам отдаются **сервером** после проверки entitlement, а не статическими чанками.
- **Цепочка поставки:** `npm ci`, lock-файлы, Dependabot/Renovate, `npm audit`, SAST (Semgrep/CodeQL), сканирование образов (Trivy), секрет-сканнер (gitleaks) в CI и pre-commit.
- **Модерация и безопасность сообщества:** жалобы, блокировки, фильтры, rate limit на сообщения/посты, решение по разделу «Знакомства».
- **Ответы API:** единый формат ошибок без внутренних деталей, request-id, корреляция с логами.

### 7.5 Инфраструктура и эксплуатация

- **Контейнеры** (Docker) для всех сервисов; на первом этапе — Docker Compose на 2+ ВМ с балансировщиком; при росте — Kubernetes (managed) или Nomad.
- **Окружения:** `dev` → `staging` → `prod`; фичи через feature flags; релизы blue/green или canary, откат одной командой.
- **CI/CD:** линтер, типы, unit + integration + e2e (Playwright), сборка образа, миграции, деплой, smoke-тест. Бэкенд и фронтенд деплоятся из одного пайплайна.
- **IaC:** Terraform/Ansible, секреты вне репозитория.
- **Автомасштабирование** stateless-сервисов по CPU/RPS/длине очереди; HPA для воркеров.
- **Наблюдаемость:** Prometheus + Grafana (RED/USE метрики), централизованные логи (Loki/ELK), OpenTelemetry-трейсы, Sentry (фронт и бэк), алерты в Telegram/PagerDuty; синтетические проверки (текущий watchdog сохранить как внешний слой).
- **SLO (предлагается):** доступность API 99,9 %, p95 чтения < 300 мс, p95 записи < 500 мс, RPO ≤ 5 мин, RTO ≤ 30 мин.

### 7.6 Аналитика v2

- **Сбор:** единая схема событий (`event`, `version`, `user_id`, `anonymous_id`, `session_id`, `ts`, `props`, `utm`, `device`), SDK во фронте, приём через эндпоинт → брокер → ClickHouse. Серверные события (регистрация, сдача ДЗ, проверка, платёж) — из доменных событий (outbox).
- **Витрины и метрики:** DAU/WAU/MAU, activation (первое осмысленное действие за 24 ч), retention D1/D7/D30 по когортам, воронки (лендинг → регистрация → первое занятие → первая сдача ДЗ), прогресс по программам, drop-off по урокам, время проверки ДЗ (SLA), нагрузка на проверяющих, вовлечённость в соцчасти, качество контента (доля верных ответов по вопросам).
- **Инструменты:** BI (Metabase/Superset/DataLens), дашборды для продукта/методистов/кураторов, алерты на аномалии (просадка DAU, рост ошибок).
- **Эксперименты:** feature flags (Unleash/GrowthBook), A/B с расчётом значимости.
- **Приватность:** согласие на аналитику, псевдонимизация, TTL, запрет текстов решений/сообщений (как сейчас).

### Этап 3 — масштабирование (4–6 месяцев)

- Несколько инстансов API за балансировщиком, автомасштабирование, реплика PostgreSQL для чтения.
- Выделение **Code Execution** (sandbox c изоляцией и квотами), **Social** и, при необходимости, **Learning** в отдельные сервисы.
- CDN перед статикой и публичным API, WAF, нагрузочные тесты (k6) перед каждым крупным набором, chaos-тесты, DR-учения.
- A/B-платформа, BI для методистов, прогнозные метрики оттока.

### Правило выделения сервиса

Выделять домен в отдельный сервис, только если выполняется **хотя бы два** условия: (1) у него иная нагрузка/масштабирование; (2) иные требования к безопасности/изоляции; (3) независимый релизный цикл или отдельная команда; (4) уже есть чёткий контракт и своя БД. Иначе — оставаться модулем монолита.

## 11. Метрики успеха перехода

- 0 критичных уязвимостей по результатам внешнего пентеста; секретов в репозитории — 0 (gitleaks).

- Правка учебного контента публикуется без релиза кода.
- Запросов polling от клиента — не более 10 % от сегодняшнего.
- Аналитика: дашборды retention/воронок доступны продукту без помощи разработчиков.
